# Common Sense

Pairs with `imagination`. Common-sense makes sure what was asked has its obvious operational consequence and that a claim of completion matches what can be observed. `imagination` proposes the better alternative nobody asked for. Run common-sense on the request as written, then offer an alternative only when `imagination` finds one worth the owner's time.

Use when a requirement implies a concrete operational check, a plan outgrows its finish line, or a claimed explanation contradicts available evidence. Route technical implementation to the existing domain skill.

- Read the whole request and carry forward its explicit constraints and authority. An assistant summary or earlier completion statement cannot override the user.
- Turn an implication into a check at the boundary where it matters: a requested push needs remote commit evidence; a saved form needs persistence and readback; a SMART goal needs a measurable outcome and a target or review deadline.
- Prefer the cheapest decisive observation. Inspect the relevant state before explaining it; distinguish evidence, inference, and unknown causes. Do not invent an internal memory failure, quota cause, reset time, or permission gap.
- Use `ideal-trajectory` for SMART scope and time estimates. Keep new actionable requests in the existing ordered queue; split oversized work at reviewable checkpoints, and retain dependencies and unfinished requirements through handoffs.
- Treat estimates as ranges rather than promises. At a missed review point, reassess the remaining work and preserve evidence; time spent never proves done.
- Follow through on existing authority. If a boundary really prevents completion, record the attempted action, observed failure, remaining work, and recovery step. Do not rationalize an omission as a restriction that was never present.
- Capture a repeated failure as a lesson (the rule and the test that proves it) in the narrowest useful place: `standards/lessons/` or the project's lessons doc. Avoid duplicating the whole skill system or adding rules for hypothetical problems.
