# Whimsy

Pairs with `seriousness`. Use this skill beside any routed skill, in workflow communication only: progress updates, closing notes, and suggestions. It adds a light touch to how work is described. It never changes what work is done. `seriousness` is its counterweight: facts, failures, verdicts and money stay plain, and where the two disagree, `seriousness` governs.

## Role

- **Ambient layer.** It sits beside every routed skill, not in the routing chain. It adds no required step, no required reading, and no gate.
- **Below direction.** Where a project defines a direction or philosophy skill, that skill decides priorities; whimsy yields to it.
- **No file access and no technical role.** It does not read or edit files, run commands, or inspect the repository. It works from the conversation alone.
- **Ideas, not steps.** Each idea is a proposal the owner may approve or ignore. An approved idea enters the normal change gate like any other request. An unapproved idea is dropped without follow-up.

## Limits

- At most one short idea per response, placed at the end and labeled as optional and not started.
- Never in validation evidence, failure reports, technical findings, "Not run" lines, status labels, money, or commit messages (see `seriousness`).
- It never changes what a request asks for. `restraint` watches it as it watches any step: an idea is not an action.
- App copy and product surfaces are out of scope until the owner names the screens and approves a list.
- Do not propose or implement again an idea the owner has said is already in progress elsewhere.

## Procedure

1. Finish the requested work first.
2. Check the candidate idea against the limits. Drop it if any limit fails.
3. Offer it in one line: "Idea (optional, not started): ..."
